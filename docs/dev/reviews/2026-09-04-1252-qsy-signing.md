# Review — #1252: the daemon acted on unsigned QSY lines

Reviewer: Fable. Reviewed **before implementation**, per the standing rule; the design that shipped
is the reviewed one plus the corrections below, all of which changed the code.

## Prompt

Sent with the finding, the two call sites, and the question framed for falsification rather than
confirmation:

> `openpulse-qsy` implements `sign_line`/`verify_line` and tests tampering. The daemon imports
> `decode` (unsigned) and never calls `verify_line`, which has no caller outside the crate. My
> instinct is that this is a live authentication gap on the shipping surface, not a dormant one, and
> that the fix is to make the signature mandatory in the codec rather than optional at the caller.
> Test that instinct rather than confirming it. Specifically: (a) is the daemon path actually
> reachable on air, or is it gated by something upstream that already authenticates? (b) is
> "mandatory in the codec" the right seam, or does it break a legitimate unsigned use? (c) what does
> a signature actually buy here — be precise about what an on-air adversary can and cannot still do.
> (d) what would falsify each of these? Flag anything wrong or unproven in my framing.

## Verdict

Confirmed as a live gap, with **five corrections** that changed the design. Each is recorded because
each came from evidence outside the crate under change.

1. **A signature alone buys nothing without a key to check it against.** My framing assumed
   "verify the signature" was the fix. It is not: `verify_line` takes whatever key the caller
   supplies, so the daemon verifying against a key read from the line itself would authenticate the
   adversary. The correct property is *authenticated to the peer the handshake established* — the
   key is pinned from `last_verified_peer()` when the negotiation opens, and a line signed by any
   other key is refused. This is the difference between a signed message and an authenticated one,
   and my framing conflated them.

2. **The format break must move the timestamp, not append it.** Freshness has to be inside the
   signed span or it is decoration. Appending it after the payload leaves a mixed-version pair
   silently interoperable on the frames whose payload happens to parse — a v1 receiver reads a v2
   line, ignores a trailing field, and acts. Placing it immediately after the token means every v1
   parse fails on the first field, so the pair fails loudly. This is why `SigningDomain::QsyLine`
   goes 1 -> 2 (a per-domain version, independent of the Frame `WIRE_VERSION` the maintainer froze
   at #1191 — confirmed with the maintainer before bumping).

3. **`sign_line` must return `Result`.** It could not fail before, which is exactly what let the
   line-length ceiling go unchecked: a `QSY_LIST` of candidates plus a base64 signature can exceed
   the frame payload, and an infallible signer has nowhere to say so. Measured after the review,
   not estimated: a `QSY_LIST` holds **6** candidates at the daemon's 8-hex-char token and **3** at
   the codec's 64-char maximum. The review's own estimate was ~7 — so the cap in `server.rs` is 6,
   from the measurement, and `MAX_QSY_LINE_BYTES` is enforced at encode.

4. **The security claim in the PR and README must be bounded.** The wording to use, and no
   stronger: *QSY lines are authenticated to the link peer established by the signed handshake and
   are subject to `allow_trustlevels`. An on-air adversary can still jam the negotiation; they can
   no longer steer it, abort it, or move a station under the peer's identity. Replay is bounded by
   the per-session token and the signed timestamp.* The README already contains the sentence this
   fix is supposed to make true, which is how a hedge hardens into a claim — so the write-up goes
   back for review before it is posted.

5. **The doc sweep is part of the fix, not follow-up.** Twelve documents assert the property as
   already true. One of them is a prior code review that **"Confirmed: signed QSY frames go through
   `verify_line()` before decoding"** — with four citations, all inside `openpulse-qsy`. The crate
   did sign; the daemon never called it. That review's request had stated the property as a premise
   and scoped the search to the implementing crate, so the confirmation was structurally unable to
   find the gap. Both files carry a correction rather than an edit, because the failure shape is
   worth keeping: *a confirmation whose citations all sit inside the implementing module has
   verified the module, not the system.*

## Rejected during review

- **Verifying opportunistically** (check the signature if present, accept the line if absent) —
  refused: it is the unsigned path with extra steps, and every adversary simply omits the field.
- **Refusing to start when `allow_trustlevels` cannot be satisfied** — out of scope here, and
  overturned separately by the maintainer: untrusted is the default for synchronized operation
  including relay and mesh; operators opt *into* restriction. The `reduced` level joins the default
  allow-list because it is precisely what a key proven over air earns.

## What this review did NOT establish

That the format break is safe for deployed stations. Nothing is deployed off `main` (the #1191
finding), which is the whole reason the break is affordable now; that premise is inherited, not
re-checked here. And the review is not the gate: `scripts/gate.sh` runs on the finished branch.
